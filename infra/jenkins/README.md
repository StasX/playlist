# Local Jenkins bootstrap

Requires Helm, kubectl, a running Kubernetes cluster, and a default StorageClass with at least 8 GiB available. The cluster must be able to pull container images and download Jenkins plugins.

From the project root, install or update the `jenkins` Helm release in namespace `jenkins`:

```powershell
.\infra\jenkins\bootstrap.ps1
```

Or use Bash (Linux, macOS, WSL, or Git Bash), with Helm and kubectl available in that environment:

```bash
bash infra/jenkins/bootstrap.sh
bash infra/jenkins/bootstrap.sh --context docker-desktop
bash infra/jenkins/bootstrap.sh --render
```

The Bash script accepts `--help` and resolves its values files relative to its own location, so it can also be called from another directory.

The script uses the current kubectl context. To select a specific cluster without changing your current context:

```powershell
.\infra\jenkins\bootstrap.ps1 -Context docker-desktop
```

Both scripts load `values.yaml`, the pinned plugin inventory in `plugins.yaml`, and the controller configuration in `casc/jenkins.yaml`. The chart version is pinned in the scripts. A separate repository configuration avoids depending on your local Helm repository cache. Plugin versions were captured from the working controller; automatic resolution of newer plugin dependencies is disabled. Update the plugin inventory deliberately when upgrading Jenkins or its plugins.

Render the manifests without installing anything:

```powershell
.\infra\jenkins\bootstrap.ps1 -Render
```

Equivalent install command:

```sh
helm upgrade --install jenkins jenkins --repo https://charts.jenkins.io --version 5.10.5 --repository-config infra/jenkins/repositories.yaml --namespace jenkins --create-namespace -f infra/jenkins/values.yaml -f infra/jenkins/plugins.yaml --set-file controller.JCasC.configScripts.jenkins=infra/jenkins/casc/jenkins.yaml --wait --timeout 15m
```

## Access and login

```sh
kubectl --namespace jenkins port-forward svc/jenkins 8080:8080
```

Open http://localhost:8080 and leave that terminal running. Username: `admin`. Retrieve the generated password in PowerShell:

```powershell
$encodedPassword = kubectl --namespace jenkins get secret jenkins -o 'jsonpath={.data.jenkins-admin-password}'
if ($LASTEXITCODE -ne 0) { throw 'Could not read the Jenkins admin secret.' }
[System.Text.Encoding]::UTF8.GetString([System.Convert]::FromBase64String($encodedPassword))
```

With a custom context, add `--context CONTEXT` to these kubectl commands. Passwords are generated by the chart; keep credentials out of values.yaml and Git. Jenkins home is stored in a persistent volume.

## Connect the existing pipeline

### Controller configuration

[`casc/jenkins.yaml`](casc/jenkins.yaml) contains the controller's Kubernetes cloud settings, security settings, and five configured shared libraries. `test-suite` is trusted and the other four libraries are untrusted.

Both bootstrap scripts load this file. Its admin security realm reads `${chart-admin-username}` and `${chart-admin-password}` from the Helm chart's Kubernetes Secret. This preserves password generation on fresh installations and the existing chart-managed password during upgrades. No password is stored in Git. Review future exports for sensitive values before committing them.

`controller.JCasC.defaultConfig` is disabled because the loadable file owns the controller's security realm, authorization, Kubernetes cloud, and other exported settings. Do not enable chart defaults alongside this full configuration: duplicate JCasC keys conflict. Edit the loadable file for future changes; changing chart values such as `cloudName` or `numExecutors` alone will not replace settings owned by that file. Its service names and namespace match this bootstrap's fixed `jenkins` release and namespace.

The exact Helm-rendered loadable YAML was checked against the running controller's `/configuration-as-code/check` endpoint, which returned HTTP 200 with no issues. Both scripts were also verified in render-only mode. These checks do not reload the running controller. Running either script without its render option installs or upgrades Jenkins and can replace UI-managed settings with the committed configuration.

This is not a complete backup: job definitions, build history, plugin binaries, and external credentials are not included. `plugins.yaml` supplies compatible plugin versions for installation; registry and SCM credentials still need to be supplied separately. When exporting again, review the diff, refresh the plugin inventory as needed, and retain the Secret references in the loadable file's security realm.

Registry and SCM credentials are managed through the Jenkins UI and saved in the persistent Jenkins home. The loadable JCasC file deliberately omits the top-level `credentials` section so restarts, configuration reloads, and Helm upgrades preserve those credentials. Remove that section from future exports as well, including empty credential domains. A fresh installation with a new Jenkins home starts without registry or SCM credentials; reinstalling with an existing PVC retains them. The chart-managed admin login is configured separately.

To export again from the UI, open **Manage Jenkins → Configuration as Code** and use **View Configuration** or **Download Configuration**, depending on the installed plugin version. See the [JCasC export documentation](https://jenkins-configuration-as-code.netlify.app/docs/export/) for export limitations.

The loaded configuration creates a Kubernetes cloud named `kubernetes`, matching the root Jenkinsfile. Build agents connect to the controller through its internal Service; localhost is only for browser access.

Before running this project's pipeline:

1. The Jenkinsfile loads `installers`, `dockerizer`, `code-qualities`, and `securityscans` from their configured GitHub repositories on branch `main`. The bootstrap also retains `test-suite` in the exported controller configuration, but the pipeline runs PHPUnit and Infection directly. These libraries are external to this repository; update the loadable JCasC file if their repositories, branches, or credential IDs change.
2. Add a **Username with password** credential with ID `dockerhub-creds`, as expected by `Dockerizer.login()`. The account must be able to push `sm1986/playlist-frontend` and `sm1986/playlist-backend`. Update the image prefix in the Jenkinsfile if publishing to another namespace.
3. Create a **Pipeline** job using **Pipeline script from SCM**, point it at this repository, select the branch containing your changes (currently `dev`), and set the script path to `Jenkinsfile`.
4. The test stage uses [`docker-compose.dev.yml`](../../docker-compose.dev.yml) inside the Docker build container to start a dedicated MariaDB database. Compose initializes `playlist_test`, waits for MariaDB to become healthy, and runs the PHP test container on the same network using host `database`. No external test database or Kubernetes Service is required. The test database stores its data in memory and is removed after the stage. The Docker container must provide the Compose plugin; the shared Jenkins workspace must be accessible to its Docker daemon for bind mounts.

Commit and push changes, then select **Build Now** to load the Jenkinsfile from SCM. **Replay** reuses the earlier build's pipeline script and can continue running outdated code even when checkout retrieves a newer commit.

The existing pipeline uses a privileged Docker-in-Docker build container, so the namespace must permit privileged build pods. The bootstrap does not grant cluster-admin permissions or change namespace policies.

### Pipeline stages and PHP setup

The PHP build container uses `php:8.5-cli-alpine` to match the application's PHP minor version. After checkout, [`infra/php/prepare-php.sh`](../php/prepare-php.sh) runs from the repository root inside that container. It installs Composer with SHA-384 installer signature verification, missing PHP extensions including `pdo_mysql`, PCOV for coverage and mutation testing, and supporting tools. It also sets PHP's memory limit to 512 MiB for static analysis. It is an Alpine container setup script, not a host setup command.

The pipeline installs backend dependencies from `composer.lock`, prepares separate Checkov and Semgrep virtual environments, and waits for the Docker daemon. The build pod needs outbound access to Alpine repositories, PECL, Composer and package sources, PyPI, scan rule sources, and container registries.

PHP CS Fixer, PHP_CodeSniffer, and PHPStan run in parallel. Security checks run Composer Audit, Semgrep for PHP and Dockerfiles, and Checkov for the three service Dockerfiles. The pipeline does not scan Compose YAML with Checkov's Dockerfile framework.

PHPUnit and Infection run sequentially through the Compose test runner because they share the workspace and test database. The test image reuses `infra/php/prepare-php.sh` and installs locked Composer dependencies in a separate volume. The stage has a 20-minute timeout and stops the Compose stack even after failure. PHPUnit writes its JUnit report to `backend/phpunit-results.xml`, keeping `backend/phpunit.xml` as the configuration file. Test results, coverage, mutation reports, and scanner reports are archived before cleanup.

The pipeline builds and scans the frontend and backend images, then pauses at **Approve Docker Image Publishing**. Check **PUBLISH_IMAGES** and select **Continue** to log in, tag, and push both images to Docker Hub. Leave it unchecked and select **Continue** to finish without publishing; **Abort** cancels the build. The current Jenkinsfile publishes version `1.0.0` for environment `dev`; change its variables when preparing another release. The database Dockerfile is scanned but its image is not built or published by this pipeline.

Build agents use temporary workspaces that are discarded when their Kubernetes pods are deleted, so the pipeline does not run a separate workspace cleanup stage. The test stage still stops its Compose stack in a `finally` block. Generated PHPStan, Infection, and formatter cache files are ignored by Git.

## Troubleshooting

```sh
kubectl --namespace jenkins get pods,svc,pvc
kubectl --namespace jenkins describe pod jenkins-0
kubectl --namespace jenkins logs jenkins-0 -c init
kubectl --namespace jenkins logs jenkins-0 -c jenkins
```

A Pending PVC usually means the default StorageClass cannot provision storage. Check `kubectl get storageclass` and set `persistence.storageClass` to an available class if needed.
